## Achado de escopo (revisão pós-Fase 5, mantenedor 2026-07-24)

Review do Codex (PR #200) achou 3 bugs reais na Fase 5 (corrigidos direto, ver commits da branch). Um deles — admin escolhe `source_platform` manualmente num `<select>`, pode divergir do HTML colado — expôs um problema maior: a spec 085 foi desenhada só pra 2 fontes (DMs Guild/DriveThruRPG, mesma família OneBookShelf), mas o mantenedor vai adicionar 100+ sites ao Modo 3 (colar HTML) ao longo do tempo. Parser hardcoded por par de `if/else` de plataforma não escala pra isso.

**Decisões nominais do mantenedor estão registradas na fonte canônica** — `spec.md`, seção "⚠️ Emenda de escopo", itens **E1–E7** (requisitos 8a/12 e um critério de aceite marcados como SUPERADOS lá, não só aqui). Este `tasks.md` executa aquela emenda; em conflito, `spec.md` prevalece.

Resumo operacional (detalhe e justificativa em `spec.md` E1–E7): registry de plataformas vai pro banco (admin cadastra via UI, sem deploy) e substitui **totalmente** o enum `DownloadSourcePlatform`; parser genérico resolve JSON-LD Schema.org só com domínio+nome cadastrados; peculiaridade de site sempre vira override em código, nunca config na UI; StorytellersVault passa a ser suportada (E3); `CRON_SOURCE_PLATFORMS`/`PRICE_CHECKABLE_PLATFORMS` viram flags na tabela; beta **não** é tratado como vazio (E7).

**Decisões de design fechadas nesta revisão (eram "decidir ao implementar", agora têm critério):**
- **D-A. Tipo de `DownloadSourcePlatform`:** híbrido `KnownSourcePlatform | (string & {})` — mantém autocomplete/DX para as plataformas de seed conhecidas, aceita qualquer string cadastrada em runtime. Critério de aceite: código existente que usa literais conhecidos (`'itch_io'`, `'dms_guild'`…) compila sem cast, E uma plataforma cadastrada só no banco também é aceita sem erro de tipo. Validação real acontece em runtime contra o registry, nunca só no tipo. **Trade-off aceito conscientemente:** o tipo deixa de ser exaustivo — um `switch` sobre `source_platform` não vai mais dar erro de compilação em caso não coberto. Hoje isso não afeta nada (verificado: nenhum `switch` sobre esse tipo no backend, só `Set.has`/`.includes`), mas quem escrever um `switch` sobre plataforma no futuro precisa de `default` explícito, não pode contar com exaustividade.
- **D-B. PK do registry:** `slug VARCHAR(30) PRIMARY KEY` (valor textual, ex.: `'dms_guild'`) — não UUID. Motivo: as 4 tabelas que hoje guardam `source_platform` já guardam esse texto; FK por slug evita reescrever todas as linhas existentes em beta e mantém as queries/logs legíveis.
- **D-C. Referência ao override no registry:** coluna `parser_kind VARCHAR(30) NOT NULL DEFAULT 'json_ld_generic'`, com `'json_ld_generic'` (sem override) ou o **slug do override** (ex.: `'onebookshelf'`) resolvido pelo mapa em código da T7.2. Nunca caminho de arquivo/módulo — banco não referencia estrutura de diretório.
- **D-D. Local da UI de cadastro:** rota nova `/gestao/plataformas` (grupo "Sistema" da sidebar, junto de Métricas/Configurações), não aba dentro de Importar — cadastro de plataforma é configuração do sistema, não parte do fluxo de importar um material.

Ver critério de aceite de 422 explícito (`unsupported_platform`/`invalid_json_ld`) como mitigação parcial (falha visível é melhor que campo errado silencioso, mas não é alarme proativo — ninguém é notificado, só o próximo admin que tentar colar HTML daquele site percebe).
