# 085 — Downloads: parser HTML determinístico para DMs Guild/DriveThruRPG

- **Módulo/Pacote:** apps/downloads/backend
- **Gate relacionado:** D (downloads já em Gate D)
- **Spec anterior relacionada:** 084 (scraper de indexação automática — fechada com débito D-084-09; DMs Guild e DriveThruRPG ficaram sem adapter automático por WAF confirmado bloqueando fetch simples, Patchright e Camoufox)

## Origem

Investigação pré-spec via 7 subagentes (3 investigadores técnicos + 3 "advogado do diabo" + 1 síntese, 2026-07-24) rodada antes deste documento. Achados completos preservados em `sessoes/` (ver sessão desta data). Resumo do que motivou as decisões abaixo:

- WAF de DMs Guild/DriveThruRPG bloqueia até `WebFetch` de agente (403 sem corpo, confirmado ao vivo) — não existe forma de obter HTML dessas páginas exceto via navegador logado do admin.
- `POST /api/v1/admin/scraper/ingest` (spec 084, `apps/downloads/backend/src/routes/scraper.ts:127-183`) já é fonte-agnóstica: aceita `items[]` no formato `ScrapedItem` e roda o mesmo pipeline (`scraperIngest.ts`) independente de como os dados foram coletados.
- Precedente direto já existe no repo: `itchIoParser.ts`/`operaRpgScraper.ts` fazem parsing determinístico de HTML de terceiro via regex-sobre-bloco isolado (sem lib nova), incluindo extração de meta tags `og:image`/`og:description`.
- Código já documenta DMs Guild como revenue-share com WotC, regra "só linkar, nunca copiar" — motivou a decisão de que o parser nunca persiste o HTML bruto colado.
- Alternativa considerada e descartada pelo mantenedor: bookmarklet/script client-side (roda no console do navegador, zero endpoint novo). Decisão nominal: manter parser server-side, mitigando o risco de cópia por **nunca persistir** o HTML recebido (nem log, nem banco — só passa pela memória do request durante o parse).

## Aprendizados do `mesas` — o que se aplica e o que não

Investigação de código real (`apps/mesas/backend/src/discord/parseLearning.ts`, `learningRules.ts`, `services/tableDuplicateDetection.ts`, `routes/discord/duplicates.ts`) antes de decidir o que herdar. O `mesas` tem 3 sistemas distintos de aprendizado — nenhum foi construído pra HTML estruturado de plataforma fixa, então a adaptação é seletiva, não cópia 1:1:

1. **Dedupe por similaridade + candidato revisado por humano (`tableDuplicateDetection.ts`) — SE APLICA, adaptado.** `mesas` calcula trigram similarity (título 0.52 + descrição 0.36 + bônus de mesma `source_url`/mesmo sistema) contra mesas ativas, pré-filtrado via `pg_trgm` no Postgres, threshold 0.75 — mas **nunca descarta automaticamente**: grava como `table_duplicate_candidates` e um humano confirma/rejeita via `PATCH /duplicate-candidates/:id`, cada decisão vira `discord_parse_feedback`. Hoje `downloads` só tem dedupe por `sourceUrl` exata (UNIQUE, `scraperIngest.ts`) — correto pro Modo 3 fonte-automática (mesma URL = mesmo item), mas **fraco pro parser HTML manual**: o mesmo produto pode ser colado 2x com URL ligeiramente diferente (parâmetro de afiliado/idioma na URL, redirecionamento), ou o mesmo material pode já existir catalogado manualmente por outro admin com título quase idêntico mas `sourceUrl` diferente. Adaptação proposta: reaproveitar `pg_trgm` (extension já habilitada no monorepo desde `migration_17` do `mesas`, mas checar se `downloads` já tem habilitada) pra alertar "possível duplicata" no preview antes do admin confirmar — nunca bloquear automaticamente, só sinalizar.
2. **Correção humana no draft vira aprendizado de rótulo/valor (`learningRules.ts`) — NÃO SE APLICA diretamente.** Esse sistema (`label_alias`, `field_value` com trava rígida contra generalizar "fatos de ocorrência" como vaga/preço/data) resolve um problema específico de texto livre em português com rótulos variáveis ("Mestre:", "Narrador:", "GM:" — sinônimos que mudam por autor/comunidade). HTML de DMs Guild/DriveThruRPG é **estruturalmente fixo** (mesmo template Angular SSR, mesmo JSON-LD schema.org para todo produto) — não há "rótulo variável" a aprender, o parser sempre lê a mesma chave (`offers.price`, `name`, etc.). Se o site mudar de layout, isso quebra pra TODOS os produtos igual, não é um caso de aprendizado incremental por ocorrência — é uma quebra estrutural que precisa de correção de código (já coberto por D-085-03). Não implementar esse sistema aqui seria over-engineering para um problema que não existe neste domínio.
3. **Cada parse vira "case" auditável + feedback linkado (`parseLearning.ts`) — SE APLICA parcialmente, sem o aparato de aprendizado.** `mesas` grava todo parse como `discord_parse_cases` (hash, features, resultado determinístico) e toda correção humana como `discord_parse_feedback` — usado tanto pra auditoria quanto pra alimentar `learningRules`. Como o item 2 acima não se aplica (nada a aprender), a parte de aprendizado fica de fora, mas a parte de **auditoria** (registrar cada extração feita, o que foi extraído vs. o que o admin efetivamente confirmou/editou antes de publicar) é útil por si só — permite ao mantenedor revisitar D-085-02 (volume real de uso) com dado real, e dá rastro pra investigar se o parser está sistematicamente errando algum campo (reforça D-085-03).

## Problema

Popular o catálogo com materiais em português de DMs Guild/DriveThruRPG hoje exige que o admin preencha manualmente cada campo (Modo 3, formulário ou payload JSON à mão) olhando a página aberta no navegador — funciona, mas é lento e sujeito a erro de digitação/esquecimento de campo. O admin já tem a página renderizada e logada no navegador (única forma de contornar o WAF); falta um jeito de transformar isso num payload pronto sem digitar campo a campo.

## Requisitos

1. Endpoint novo (ex.: `POST /api/v1/admin/scraper/parse-html`) recebe `{source_platform: 'dms_guild' | 'drivethrurpg', html: string}` de admin autenticado (`authMiddleware` + `requireRole('admin')`, mesmo padrão das rotas de `scraper.ts`).
2. Extração combina 2 fontes complementares do mesmo HTML colado, cada uma escolhida pelo campo que resolve melhor (confirmado contra 3 fixtures reais — 1 DMs Guild + 2 DriveThruRPG, shape idêntico; um 3º fixture colado pelo mantenedor era na verdade `storytellersvault.com`, marca irmã OneBookShelf fora do escopo desta spec — ver requisito 8a):
   - **JSON-LD** (`<script type="application/ld+json">`, `@type: Product`): `name`→title, `description` (nota: vem truncada com "..." no fim — ver requisito 4a), `brand.name`→publisherName.
   - **Meta tags/tags soltas fora do JSON-LD** (mais confiáveis que os campos equivalentes do JSON-LD nesses 3 fixtures): `<link rel="canonical">`→sourceUrl (JSON-LD tem `offers.url` mas `canonical` é mais limpo, sem parâmetro de tracking); `<meta property="og:image">`→coverImageUrl (JSON-LD só tem `image` como **path relativo** tipo `"8957/472734.png"`, sem domínio — `og:image` já vem absoluto no CDN, evita lógica de resolver URL relativa); `<html lang="...">`→sourceLanguageHint (mais direto que inferir de outro lugar).
   - Nenhuma lib DOM nova necessária — todos os 4 sinais são blocos/atributos isolados por regex ancorada (mesmo padrão de `itchIoParser.ts`/`operaRpgScraper.ts`), sem precisar de parser HTML completo.
3. **Saída de `/parse-html` é um shape de PREVIEW próprio, diferente do `ScrapedItem`/`ingestItemSchema` que `/ingest` exige.** Achado real: `ScrapedItem.isFreeOrPwyw` (`apps/downloads/backend/src/services/scrapers/types.ts:10`) é `boolean` puro, sem estado "incerto", e `ingestItemSchema` (`scraper.ts:131`) exige `z.boolean()` — não há onde representar "preço ambíguo, admin decide" dentro desse shape estrito. O preview devolvido por `/parse-html` inclui todos os campos de `ScrapedItem` MAIS: `extractedPriceValue: number | null` (valor numérico bruto extraído, ex.: `4.00` ou `0.00` — ver requisito 4), `priceSignal: 'pwyw_tag_present' | 'zero_price_no_pwyw_tag' | 'nonzero_price_no_pwyw_tag'` (qual sinal foi usado, pro admin entender o "porquê" da sugestão, não só o resultado). O admin revisa cada campo — principalmente o preço — e só então monta o payload final (`ScrapedItem` estrito) que vai pro `POST /ingest` já existente. Nunca publica direto (mesmo padrão two-step do `mesas`/`parseTextForPreview`: analisar → revisar → confirmar).
4. **`isFreeOrPwyw` — sinal estrutural real, não texto solto ambíguo, mas o preview SEMPRE mostra o preço numérico bruto pro admin, nunca só o boolean.** Achado confirmado contra os 3 fixtures: existe uma tag específica no HTML, presente **somente** quando o produto é PWYW — `<obs-product-format-pwyw-options>` (contém o texto "Apoie o criador ao pagar mais do que o preço sugerido" e múltiplos botões de preço `$X.00`). Nos 2 fixtures de produto grátis fixo, essa tag está ausente e só existe `<p class="cy-prc">$0.00</p>`. Regra de extração (populam `priceSignal`/`extractedPriceValue` do requisito 3, o preview NUNCA pré-preenche `isFreeOrPwyw` como certeza absoluta sem o admin ver o preço-base): presença da tag PWYW → sugestão `isFreeOrPwyw: true`, `priceSignal: 'pwyw_tag_present'` (confiança alta, mas preço-base exibido — pode ser >$0, é o mínimo sugerido, não implica pago); ausência + preço extraído = `$0.00`/`0` → sugestão `true`, `priceSignal: 'zero_price_no_pwyw_tag'` (grátis fixo, confiança alta); ausência + preço > 0 → sugestão **não pré-marcada**, `priceSignal: 'nonzero_price_no_pwyw_tag'`, preview exibe alerta "produto parece pago, fora do critério D119 (só grátis/PWYW) — confirme antes de publicar". **Corrige a hipótese anterior desta spec** (que assumia JSON-LD sozinho como ambíguo e propunha marcar sempre como baixa confiança) — o sinal real está fora do JSON-LD mas é estrutural (tag DOM), não heurística de texto solto tipo "Pague quanto quiser" (esse texto aparece igual nos 3 fixtures como link de MENU de navegação lateral, não como sinal do produto — achado real que quase virou falso positivo).
4a. `description` do JSON-LD vem truncada (ex.: termina em "...") nos 3 fixtures — sinalizar no preview que a descrição pode estar incompleta, admin decide se edita/completa antes de confirmar (não é erro do parser, é como a plataforma expõe o dado nesse campo específico).
5. Campo obrigatório ausente (`title` do JSON-LD, ou nem `<script type="application/ld+json">` nem os sinais complementares presentes) → erro 422 explícito com mensagem clara, nunca fallback silencioso que inventa/adivinha valor.
6. **HTML recebido nunca é persistido** — não grava em banco, não aparece em log de request/erro/APM. Validar (ou excluir explicitamente) qualquer middleware de log do backend `downloads` que capture `req.body` antes de habilitar esta rota.
7. **Rejeitar HTML acima de um limite de tamanho, checado dentro do próprio handler** (não middleware de body-parser dedicado — achado real: `server.ts:67` já tem `express.json({ limit: '4mb' })` global, cobrindo os 3 fixtures reais confirmados de 133-155KB com folga ampla; reconfigurar limite por rota em Express não é trivial sem risco de afetar outras rotas do mesmo router, e não é necessário aqui). Handler faz `if (html.length > LIMIT) return 422` logo no início, antes de qualquer regex/parse — `LIMIT` calibrado bem acima do maior fixture real (ex.: 1MB, ~6-7x o maior fixture visto).
8. Checagem de sanidade antes de rodar qualquer extração: HTML precisa conter `<script type="application/ld+json">` com `@type: "Product"` E `<link rel="canonical">` apontando pro domínio esperado do `source_platform` informado (`dmsguild.com` para `dms_guild`, `drivethrurpg.com` para `drivethrurpg`) — rejeita com 422 cedo se faltar qualquer um dos dois, se o domínio do `canonical` não bater com o `source_platform` declarado, ou se o admin colar algo errado (PDF em base64, JSON solto, página de outro site).
8a. **Escopo restrito aos 2 domínios exatos, marcas irmãs OneBookShelf ficam fora.** Achado real: um dos 3 fixtures reais colados nesta investigação era na verdade `storytellersvault.com` (White Wolf/Vampire), mesma plataforma/template OneBookShelf mas domínio e marca diferentes — `DownloadSourcePlatform` (enum do banco) não tem valor pra essa nem outras marcas irmãs (DriveThruComics, WargameVault, Pathfinder Infinite etc.). Decisão desta spec: rejeitar com 422 claro ("domínio não suportado — só dmsguild.com e drivethrurpg.com") em vez de tentar generalizar pra família toda — evita decidir sozinho um enum novo/mapeamento de marca sem o mantenedor validar se há interesse real em outras marcas OneBookShelf. Se o mantenedor quiser cobrir mais marcas depois, é extensão futura (enum novo + spec própria), não algo a inferir aqui.
9. Saída do extrator usa schema Zod fechado (equivalente a `.strict()`) — nunca permite vazamento de campo não previsto (ex.: `rawHtml`, `debugMatch`) para o pipeline de ingest.
10. Validação de URL nos campos extraídos (`sourceUrl`, `coverImageUrl`): rejeitar scheme diferente de `http`/`https` e host claramente interno/privado (ex.: `localhost`, IP de metadata endpoint) — mitigação a SSRF/XSS de baixo risco caso esses campos sejam usados em fetch futuro ou renderizados sem sanitização.
11. `description` extraída segue a mesma regra de sanitização já obrigatória em `AGENTS.md` para HTML de terceiro (DOMPurify antes de qualquer persistência/render) — mesmo tratamento hoje devido ao Modo 3 manual, aplicado aqui também.
12. Escopo restrito a `dms_guild` e `drivethrurpg` (as 2 fontes bloqueadas por WAF, sem adapter automático). Fontes com adapter funcionando (itch.io, Grimórios & Dados, OPERA RPG) não usam esta rota — `source_platform` do payload é validado contra essa allowlist de 2 valores, não reaproveita a lista completa de `ADAPTERS` do scraper automático.
13. **Dedupe por similaridade (adaptado de `tableDuplicateDetection.ts` do `mesas`), não só `sourceUrl` exata.** Antes do admin confirmar o preview, checar título/descrição extraídos contra `download_material` existente via trigram similarity (`pg_trgm`, threshold a calibrar — `mesas` usa 0.75) — se houver candidato acima do limiar, sinalizar no preview como "possível duplicata" com link pro material existente, mas **nunca bloquear ou descartar automaticamente**: decisão de publicar mesmo assim (ou não) é sempre do admin. Verificar se `pg_trgm` já está habilitada no banco `downloads` antes de assumir — se não, extensão nova exige a mesma pergunta prévia de lib/dependência nova.
14. **Cada extração vira registro auditável mínimo** (adaptado de `discord_parse_cases`, sem o aparato de aprendizado de rótulo que não se aplica aqui — ver seção "Aprendizados do `mesas`"): registrar, por chamada ao `/parse-html`, quais campos foram extraídos com sucesso vs. quais vieram vazios/de baixa confiança, e (depois, quando o admin confirma via `/ingest`) se o valor final publicado bateu com o que o parser sugeriu ou foi editado. **Sem gravar o HTML bruto** (requisito 6) — só o resultado estruturado da extração e o resultado final confirmado. Objetivo: dar dado real pra revisitar D-085-02 (vale o investimento?) e D-085-03 (parser está sistematicamente errando algum campo?) depois de uso real, sem precisar perguntar de novo ao mantenedor "quantas vezes usou".
15. **Material publicado por este parser nunca é re-checado de preço automaticamente — limitação herdada, documentar explicitamente.** Achado real: `priceRecheckJob.ts:20` (`PRICE_CHECKABLE_PLATFORMS`, spec 084) exclui `dms_guild`/`drivethrurpg` do job diário de re-checagem de preço pós-publicação (mesmo WAF que bloqueia o scraper automático bloqueia essa re-checagem). Consequência real: se um produto catalogado via `/parse-html` mudar de PWYW/grátis pra pago fixo depois de publicado, ninguém percebe automaticamente — só via denúncia/checagem manual. Esta spec não resolve isso (resolver exigiria contornar o mesmo WAF, fora de escopo — ver "Fora de escopo"); só torna a decisão de catalogar essas fontes mais informada, sabendo que o material fica sem essa rede de segurança que `itch_io`/`grimorios_e_dados` têm.

## Critérios de aceite

- [ ] Endpoint novo protegido por `role=admin`, rejeitando não-admin com 401/403 (mesmo padrão de `scraper.ts`).
- [ ] HTML real de pelo menos 1 página de produto de cada fonte (DMs Guild, DriveThruRPG) — colado manualmente pelo mantenedor, logado, via "Copiar elemento" pós-Angular renderizado (não `Ctrl+U`/view-source, que não tem o JSON-LD injetado por JS) — vira fixture de teste antes de qualquer implementação. Sem esse fixture real, nenhuma task de implementação começa (achado da investigação: `WebFetch` bloqueado nos dois sites, ninguém validou estrutura real ainda).
- [ ] Teste confirma que campo obrigatório ausente retorna 422 com mensagem clara, nunca 200 com campo inventado.
- [ ] Teste confirma que HTML colado nunca aparece em nenhum log (grep na saída de log do backend durante teste de integração).
- [ ] Teste confirma rejeição de payload acima do limite de tamanho definido.
- [ ] Teste confirma que schema de saída rejeita/ignora campo extra não previsto.
- [ ] Preview sempre expõe `extractedPriceValue` (número bruto) e `priceSignal` (qual sinal gerou a sugestão) junto com `isFreeOrPwyw` sugerido — admin nunca vê só um `true`/`false` sem contexto de preço (requisito 3/4).
- [ ] Teste confirma que produto com preço > 0 e sem tag PWYW nunca é sugerido como `isFreeOrPwyw: true` — preview mostra alerta explícito, não publica silenciosamente como grátis.
- [ ] Teste confirma que HTML de domínio fora da allowlist (`storytellersvault.com` ou qualquer outro) retorna 422 claro, mesmo tendo JSON-LD `@type: Product` válido (requisito 8a).
- [ ] `pnpm verify:api`, lint, build, test verdes (backend `downloads`).
- [ ] Smoke real: admin cola HTML de 1 produto de cada fonte em ambiente beta, confirma preview, envia pro `/ingest`, item aparece corretamente no catálogo público.

## Fora de escopo

- Bookmarklet/script client-side (alternativa avaliada e descartada nominalmente pelo mantenedor nesta spec — pode voltar como spec própria futura se o parser server-side se mostrar caro de manter).
- Extrair de itch.io/Grimórios & Dados/OPERA RPG via este endpoint — essas fontes já têm adapter automático funcionando; esta rota é exclusiva das 2 fontes bloqueadas por WAF.
- Resolver o WAF em si (fetch/headless automatizado contra DMs Guild/DriveThruRPG) — já tentado e documentado como bloqueado na spec 084 (`blockedSourceScraper.ts`), não é objetivo desta spec.
- Detecção/correção automática de layout mudado — se o parser passar a falhar sistematicamente após redesign do site, é reportado como bug/débito na hora, não coberto por auto-detecção nesta spec.
- Auditoria de longo prazo de "quem colou o quê" — fora de escopo por ora; se o mantenedor quiser rastreabilidade de uso desta rota, é extensão futura (e essa auditoria, se vier, também não pode persistir o HTML bruto, só metadado da ação).

## Riscos e impacto em outros módulos

- **Risco jurídico residual:** mesmo sem persistir HTML, o ato de enviar o HTML da página de produto num POST para o backend do Artifício já é uma forma de cópia temporária (RAM/request). Mantenedor decidiu que isso é aceitável desde que nunca persista — risco residual pequeno mas não zero; registrar como aceito conscientemente, não como resolvido.
- **Dependência de fixture real:** sem o mantenedor colar HTML real de cada fonte primeiro, a implementação fica especulativa (mesmo erro que `fetch-and-ingest.mjs` já cometeu na spec 084, nunca confirmado). Bloqueante de verdade, não cosmético.
- **Volume ainda desconhecido:** mantenedor respondeu "não sei ainda, vou descobrir usando" sobre frequência de uso — se o volume real for baixo, o investimento desta spec pode não se pagar; decisão de revisitar isso fica registrada aqui, não é motivo pra não implementar agora (já decidido seguir com parser server-side).
- **Nenhum impacto em `packages/*` ou outros apps** — mudança isolada em `apps/downloads/backend`, reaproveitando rota/pipeline já existente da spec 084.
- **Lib nova a decidir em `plan.md`:** regex-sobre-bloco (sem lib, padrão já usado em `itchIoParser.ts`) resolve a extração do JSON-LD sem dependência nova. Meta tags soltas fora do JSON-LD podem exigir extração mais robusta — se precisar de lib (`cheerio`/`linkedom`), perguntar ao mantenedor antes de instalar, por regra do `AGENTS.md` (nenhum backend do monorepo tem hoje).
- **Material publicado por este parser fica sem re-checagem de preço automática** (requisito 15) — `priceRecheckJob.ts` já exclui `dms_guild`/`drivethrurpg` por não ter parser de preço confiável pós-publicação (mesmo WAF). Risco herdado da spec 084, agora mais relevante porque esta spec ativamente populariza essas 2 fontes.
- **Escopo restrito aos domínios exatos `dmsguild.com`/`drivethrurpg.com`** (requisito 8a) — marcas irmãs OneBookShelf (StorytellersVault, DriveThruComics, WargameVault, Pathfinder Infinite) ficam de fora conscientemente, sem inferir enum novo sem o mantenedor decidir se há interesse real nelas.
